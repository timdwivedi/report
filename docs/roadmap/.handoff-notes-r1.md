## Phase 2: The Architect
- **I did:** Created a comprehensive 20-step master build plan (`07_master_plan_r1.md`) organized into 6 phases (A through F), covering data model foundation, core UX corrections, pricing engine upgrade, new modules, portal/tools, and polish/demo prep. Also created a plain-English ELI5 summary (`06_whats_left_eli5.md`) for non-technical stakeholders (Trevor, Aaron) explaining what works, what is being built next, and what comes after. Audited the full codebase: 480-line type system, 179-line quoting engine, 1,974-line demo data provider, 21 API routes, 18+ dashboard pages, sidebar navigation, and admin panel.
- **I chose:** (1) To rename the `DecorationLocation` string union type to `DecorationPosition` so the term "decoration location" can refer to the new first-class object without type name collision. (2) To model vendor-specific matrices as a `vendor_id` field on the existing `DecoratorMatrix` interface (null = org default) rather than a separate join table -- simpler and sufficient for V1. (3) To keep `in_hands_date` as the code-level field name but display "Enhanced Date" in all UI labels via label maps -- industry-correct display without confusing code. (4) To scope the tickets page as display-only with demo data (no create/edit CRUD) since full ticketing is P1 but having the page shows Aaron the lifecycle vision. (5) To preserve the existing Programs page code in comments rather than deleting it, since "Coming Soon" is temporary and the full module will return. (6) To structure the build plan in 5 recommended sessions, with Session 1 (foundation types) being the hardest since everything else depends on it. (7) To keep the sidebar label as "Clients" (not "Companies") since the Surgeon noted Trevor did not specify a preference, and "Clients" is more natural for the CRM context.
- **Watch out:** (1) Step 3 (decoration locations as first-class objects) is the single highest-risk step. The current `LineItemDecoration` interface has `location: DecorationLocation` (a string), `method`, `color_count`, and `decoration_cost`. The new model makes each decoration location a full object with its own `vendor_id`, `decorator_matrix_id`, `setup_cost`, `run_charges[]`, and `production_file_url`. This cascades through the quoting engine, project detail page, and demo data. Build Step 2 (vendors) BEFORE Step 3. (2) The quoting engine currently uses hardcoded tier arrays (`SCREEN_PRINT_TIERS`, `EMBROIDERY_TIERS`, etc.). The contract/all-in split (Step 8) requires the engine to accept either a product-level `vendor_cost` OR the full `blank + decorations + charges` calculation. The branching logic must be clean -- no mixing of paths. (3) Demo data refresh (Step 19) is deceptively large. Every entity must be internally consistent: project line items must reference real product IDs, which reference real vendor IDs, which have real matrices. A single broken reference will cause the demo to show "undefined" somewhere. (4) The size-tier blank cost feature (S-XL same, 2XL higher, 3XL+ higher) is important but not currently modeled. The `BlankCost` interface only has min/max quantity tiers. Size-tier costs need a separate structure or an extension to the existing one. (5) The `ContactRole` type (`primary | order | finance | marketing | other`) does not match Trevor's terminology (`billing | finance | shipping | primary | all`). Step 6 needs to reconcile these.
- **Left open:** (1) **Sidebar label "Clients" vs "Companies"** -- defaulted to "Clients" but Trevor may have a preference. Ask on next call. (2) **Products in sidebar** -- Trevor's dictated sidebar order did not mention Products. Currently it exists as a sidebar item. Kept it but it may need to move under Settings or be removed from top-level nav. Ask Trevor. (3) **Size-tier blank cost modeling** -- need to decide between adding a `size_tier` dimension to the existing `BlankCost` interface vs. a separate `SizeTierCost` structure. Both work; one is a design choice. (4) **Floor stock entity structure** -- the Surgeon recommended planning the entity structure now even though UI is Round 3+. The plan does not include this. Could add type definitions to `app.ts` without building UI. (5) **Creative request assignment model** -- for V1, hard-coded to Boundless creative team. The interface has `assigned_to: string` which works for both human names and future AI agent IDs, but the UI pattern (dropdown of team members vs. AI agent selector) was not specified. (6) **Reorder portal data model** -- Step 17 is concept-only. The actual data model for persistent client "shops" with pre-configured products and their own price breaks needs design in Round 2.
- **Status:** CLEAN
